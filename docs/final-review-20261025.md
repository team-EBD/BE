# 최종 점검을 위한 BE 분석 (2026-10-25)

분석 기준: 평가의견(2026-06-04, 2026-08-24), 팀·멘토 논의의 요구사항, BE `origin/main`의 `dc11453`. 원본 사적 대화나 사용자별 운영 데이터는 이 문서에 포함하지 않는다.

## 현재 구조

- `app/services/analyze.py`: AI 후보 → 정확한 음식명 DB 매칭 → 영양 출처 선택 → 섭취 g 환산 → 후보·호출 로그 저장. 사진·문장 입력이 공통 후처리를 사용한다.
- `app/services/matching.py`: 사진 음식명은 정규화 후 정확 일치만 사용한다. 과거 포함/유사도 오매칭을 피하는 정책이다. 문장 입력에는 DB 후보명·제공량을 먼저 보내는 검색 보강이 이미 있다.
- `app/services/recommend/`: 음식군, 개인 빈도, 영양·음식 유사도, 전체 인기, 협업, 밴딧, 최근 섭취·피드백을 조합한다. 이 경로의 추천 이유는 템플릿이며 추가 LLM 호출이 없다.
- `app/services/meals.py`: 사용자가 확정한 영양 합계, 선택 후보, 수량 변경을 저장한다. 저장 API에 들어오는 영양은 이미 FE에서 수량을 적용한 합계이다.
- `.github/workflows/deploy.yml`: feat → dev는 통합·검증, main 푸시는 pytest와 Postgres 마이그레이션 검증 뒤 AWS SSM 배포. README의 오래된 Cloudtype 자동 배포 설명보다 실제 워크플로가 현재 동작을 나타낸다.

| --- | --- | --- |
| 개수/용량과 포장 열량의 기준 혼동 | g × 100g당 영양, 사진 포장 용량 우선 사용 | 인쇄 열량에 내부 낱개 수를 곱하고, 구 앱 반올림이 g를 바꾸는 결함을 발견·수정했다. |
| 0 kcal 소형 제품/음료 오류 | 인쇄 열량 우선 경로 존재 | 0을 값 없음으로 취급하는 결함을 발견·수정했다. |

| 외부 검색 표시성분 신뢰 | `label > DB > AI` 우선순위와 출처 URL 응답 | AI 측에서 실제 근거 URL·제품 일치·숫자 검증이 필요하다. 출처가 있다는 것만으로 OCR·검색 정답이 보장되지는 않는다. |
| 신뢰도에 따른 자동 처리 | 음식 후보 `confidence_score`, 영양 `nutrition_source` 제공 | 음식명 신뢰도와 양·영양 오차는 다른 변수다. 현재 점수를 실측 정확도 확률로 해석할 근거는 부족하다. |
| 사용자 보정 부담 | 절대 g, 낱개 수량, 식습관 보정, DB 문장 선매칭 | 국물 제외0.7/소스 제외0.85는 고정 휴리스틱이다. 음식별 실제 섭취 영양을 측정한 계수가 아니다. |
| 사용자 이력 활용 부족 | 추천의 빈도·유사도·협업, 즐겨찾기/자주 먹는 음식 경로 존재 | 이전 식사의 동일 포장·동일 양을 사진에서 자동 확정하는 기능으로 간주하면 안 된다. |
| 정확도/보정률의 근거 부족 | 후보 선택·보정로그·호출 지연과 입력 유형 기록 | 식단 저장 연결과 보정값은 선택 필드이며 구 앱·누락 입력은 판정 불가일 수 있다. 미저장을 오인식으로, 성공응답을 정답으로 간주하면 안 된다. |

| 추천 제약과 성과 | 음식군 중복·끼니 예산·최근 섭취·단백질·행동 반영 | 알레르기나 의료 상황에 대한 안전한 추천 시스템으로 검증된 것은 아니다. 추천 채택/실섭취와 장기 리텐션은 별도 지표다. |

## 이번에 검증한 가설

포장 열량의 동일 중량 기준 사용, 원래 개수와 표시 개수의 분리, 명시적인0 kcal 처리라는 세 가설을 구현했다. [실험 문서](../experiments/packaged_nutrition_20261025/README.md)에 코드 실행 명령, 합성 입력, 이전 main 비교, 결과와 한계를 저장했다. 기존 API·DB 스키마·FE 변경 없이 적용 가능한 계산 결함이다.

실험은 합성 계약 사례18개에서 통과9→18, 기존 통과 사례의 회귀0을 확인했다. 실제 사진 정확도·사용자 보정률·리텐션 개선은 측정하지 않았다. 새 벡터 DB나 추가 외부 모델 호출은 이 산식 결함을 해결하는 데 필요하지 않다.

후속 교차 검토에서 기존 FE가 포장 원문 용량을 1표시단위 기준으로 읽는 불일치를 확인했다. BE 응답의 `size_text`만 표시당 g/ml로 정규화하여 반개45g의135 kcal가 `1개90g`으로 표시되던 문제를 해결했다. FE는 수정하지 않았으며 실제 FE 함수를 읽어 실행한 합성 표시 사례12개가 모두 통과했다(수정 전4개). 기존 열량18개 실험 결과는 유지된다. 응답의 원래 포장 `size_g`와 기타 제품 정보·AI 입력 객체는 보존하지만 성공 응답 원문을 DB에 영구 보관하는 기능은 기존에도 없으므로 별도 증빙 보존으로 주장하지 않는다.

## 후속 검증 기준

1. 실제 라벨 사진을 포장 전체/1회분/100g당, 낱개/묶음, 부분 섭취로 분리하고, 인쇄 글자·실측 중량·정답 kcal를 독립 기록한다. 사진 명칭 정확도, 양 오차, DB/라벨 연결 오류, 최종 kcal 오차를 따로 계산한다. **결과 확인후 추가 혹은 수정필요**.
2. 운영 전후 비교에서는 팀/테스트 계정, 튜토리얼, 앱 버전, 사진 수, 음식군, 새/재방문 사용자를 구분한다. 저장 연결 없음·판정 불가를 제외할지 포함할지 분모를 명시한다. **결과 확인후 추가 혹은 수정필요**.
3. RAG·이력 기반 후보 재정렬·모델 라우팅은 같은 검증셋에서 기준 모델과 비교하고, 오연결률·사용자 보정률·지연·호출 비용을 함께 확인한 뒤 채택한다. 현재 결과로 이 가설들이 검증됐다고 주장하지 않는다. **결과 확인후 추가 혹은 수정필요**.
