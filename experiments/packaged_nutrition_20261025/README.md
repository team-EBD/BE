# 포장 열량·섭취량 정합성 실험 (2026-10-25)

## 문제와 범위

기획심의(2026-06-04)와 중간점검(2026-08-24)은 사진 기반 양 추정, 개수·용량 및 소형 제품의 단위 열량 오류, 수동 보정 부담, 재현 가능한 검증 근거 부족을 지적했다. 현재 구현에는 정확한 음식명 DB 매칭, g × 100g당 영양 계산, 포장 정보/검색 표시성분 우선순위, 텍스트 입력 시 DB 후보 제공이 이미 있다. 추천에도 음식군·빈도·유사도·협업·밴딧이 구현되어 있다. 추가 RAG를 도입하기 전에 기존 후처리의 산식 오류를 분리하여 검증했다.

AI 계약의 `package.printed_kcal`는 **사진 속 포장 전체 열량**, `package.size_g`는 **그 포장에 인쇄된 용량**이다. BE의 기존 계산에는 다음 문제가 남아 있었다.

1. 봉지 속 낱개 수를 포장 수로 취급하여 포장 전체 열량에 곱한다.
2. 구 앱 호환을 위한 소수 개수의 정수 반올림이 실제 포장 섭취 g와 열량까지 바꾼다.
3. `printed_kcal=0`을 값 없음으로 취급하여 다른 밀도로 덮어쓴다.

## 가설과 구현

| 가설 | 구현 | 합성 사례 수 |
| --- | --- | ---: |
| H1: 같은 포장의 중량 기준을 사용하면 포장/내부 낱개 혼동을 줄일 수 있다. | 사진의 포장 열량 × 섭취 g / 사진의 포장 g. 포장 g가 없고 여러 '개'라면 기존 밀도 계산으로 복귀한다. | 3 |
| H2: 표시용 개수와 원래 관측 개수를 분리하면 앱 호환 모드에서도 섭취량을 보존한다. | `observed_count`로 포장 g를 계산하고, 표시용 반올림 후 1단위 영양값을 다시 나눈다. | 4 |
| H3: 0을 유효한 숫자로 처리하면 명시적인 0 kcal가 유지된다. | None 여부와 유한·비음수 조건을 검사한다. | 2 |
| 대조 사례 | 낱개 포장 1/2개, 반개 지원 모드, 캔, 잔, DB 음식, 구 AI 응답 계약을 유지한다. | 9 |

검색 라벨의 묶음 용량을 사진에 읽힌 열량의 분모로 사용하지 않는다. 검색 제품과 사진 포장의 크기가 다를 수 있기 때문이다. 음수/NaN/무한대 인쇄 열량은 기존 밀도 경로로 복귀한다. FE가 사용하는 `nutrition`의 1단위 값 × `estimated_serving` 계약과 API 필드는 유지된다. DB 모델/마이그레이션, FE, 운영 설정을 변경하지 않았다.

### 후속 교차 검토: 앱 표시 기준량

초기 계산 수정 후에도 구 앱이 `package.size_text`를 1단위 용량으로 우선 표시하는 경로에서 불일치가 남았다. 예를 들어 반개45g의135 kcal는 계산이 맞지만 포장 원문90g 때문에 화면에 `1개 90g`으로 보였다. 내부 낱개4개120g도 전체 포장의100g 대신 1개30g을 표시해야 한다.

응답 생성 시에만 `size_text`를 표시 수량당 g/ml에 맞췄다. 원문에서 단위가 명확할 때만 같은 차원의 단위로 정규화한다(kg→g, L→ml). g↔ml를 추정 변환하지 않는다. 원문 단위를 확인할 수 없으면 `size_text=None`으로 내려 기존 앱의 계산 기준량 표기를 사용한다. `size_g`가 없어도 원문 단위와 섭취 g/표시 개수가 있으면 정규화한다. 기존에 크기가 맞는 포장과 개수 없는 음식은 원래 표기를 유지한다.

FE 파일은 수정하지 않았다. `run_display_experiment.py`는 실제 `candidateToFood.js`와 `servingBasis.js`를 읽어 Node에서 실행한다. [display_cases.json](display_cases.json) 합성12개에서 초기 계산 수정 상태의 표시4/12 → 표시 정합성 수정 후12/12를 확인했다. [display_results.json](display_results.json)에 원문·응답·실제 FE 표시·사용한 FE 소스 해시를 남겼다. **기존 열량 실험18개 결과(9→18)는 변하지 않았다.**

AI 입력의 `cand.package` 객체, 응답의 `size_g`·브랜드·제품명·변형·`label_text`는 변하지 않으며 응답 필드를 추가하지 않았다. 다만 **성공한 분석의 원문 `size_text`를 DB에 영구 보존하는 경로는 현재 없다**. `FoodCandidate`는 g·개수·출처를, `AiCallLog`는 호출 메타데이터를 저장한다. AI의 `response_logging`도 실패 시 안전화된 응답 일부만 남긴다. 이번 변경에서 메모리 원본을 보존한다는 사실을 영구 원본 로그 보존으로 해석하면 안 된다.

## 재현

BE 루트에서 실행한다. 외부 AI 호출이나 운영 DB 연결 없이 실행된다. 실험은 `DATABASE_URL=sqlite://`를 프로세스 내부에서 설정한다. 과거 비교는 git에서 **계산 함수만** 읽어 실행하며 체크아웃과 파일 변경을 하지 않는다.

```powershell
venv/Scripts/python experiments/packaged_nutrition_20261025/run.py

```

## 해석 한계 및 후속 검증

- 18개는 결함을 드러내도록 구성한 합성 계약 사례이며 무작위 실제 사진 표본이 아니다. 9→18 통과를 사진 정확도 또는 실제 칼로리 오차율 개선으로 보고하면 안 된다.
- 사진에서 읽은 열량이 전체 포장 기준이고 `size_g`가 같은 포장을 가리킨다는 AI 계약에 의존한다. OCR 자체가 100g당/1회분/총포장을 잘못 구분하면 이 산식만으로 바로잡을 수 없다.
- 섭취 g가 추정치인 경우 그 추정 오차가 남는다. 중량을 알 수 없는 여러 '개'에 포장 열량을 무조건 적용하지 않는다.
- 열량과 탄단지는 서로 다른 출처를 사용할 수 있다. 이 실험은 탄단지를 임의로 열량에 맞추는 규칙이나 실제 영양성분의 정확성을 검증하지 않는다.
- 실측 음식·라벨 사진을 별도 확보하여 포장 단위/OCR/섭취량 오류를 구분한 평가가 필요하다. **결과 확인후 추가 혹은 수정필요**.
- 배포 후 실제 보정률·초안 채택률·이탈률 변화는 별도 관찰 대상이다. 운영 API 성공률은 인식 정확도가 아니다. 현재 결과로 리텐션 인과효과를 주장하지 않는다. **결과 확인후 추가 혹은 수정필요**.
